# Phase 4B-2 — Level C 作物面积天气证据系统：总体路线

状态：**已批准**（2026-10-07）。本版把用户提供的总体路线整合进原计划（见第 8 节"决定记录"）。

**4B-2 的目标**：建立一套受科学约束、在生产中稳定运行的"作物面积 × 天气"证据系统。
这套系统要在 **2027 年美国玉米生长季开始前完成方法冻结**，然后在生长季里做前瞻性观察和评估。
剩下的工作不是一串互不相关的功能，而是同一套证据架构的组成部分。

## 2. 适用于所有剩余工作的科学不变量

- **Level C 的含义**是"制图玉米面积 × 格点天气"的筛查。它**不是**以下任何一项：
  - 受影响面积、受损面积、确认胁迫面积
  - 局地吐丝面积
  - 产量损失、产量减少
- USDA 全州作物进度数据**只能作为背景**。**不得**把全州的生育期百分比和空间天气重叠面积相乘，
  去推算局地的生育期面积。
- **不做 0–100 的综合风险分数**。热、VPD、降水、湿涝各自是独立的证据维度，彼此保持独立。
- 4B-2 期间**不把任何 Level C 证据接入生产告警或邮件**。是否接入，要等验证（4C）之后再决定，
  并且不预设一定会接入。
- 其余边界沿用 `PHASE4B0_CORN_AGRONOMIC_SPECIFICATION.md`：N 节的架构和关卡、O 节和 P 节的参数分级、
  Q 节的禁止事项、R 节的冻结与验证协议。

## 3. 每个阶段的完成标准（九项全部满足才算完成）

1. 方法和规格写成文档。
2. 实现。
3. 自动化测试。
4. 失败和缺数据的情况都有测试覆盖。
5. 用真实数据做合理性检查。
6. 有数据来源记录，有版本号。
7. 证据登记表已更新，规则从 `draft` 改为 `reviewed`，并且这一改动随 PR 一起合并。
8. 文档或报告写好，放进 `docs/`。
9. 告警和邮件的行为没有发生意料之外的变化。

## 4. 各阶段要点

### 加固（只动基础设施，保持小范围）
- 依赖线上 `public/data` 内容的回归测试，一律改为读取 `tests/fixtures` 里的冻结副本。
- 少数保留下来的真实数据检查，只校验结构，必须能接受各种如实的故障形态。
  由 `tests/liveDataOutage.test.js` 强制执行，并列出允许读取线上数据的测试名单。
- 10 月 19 日以后，确认换到 Ubuntu 26 后的第一次定时运行一切正常。

### 4B-2.2 VPD 和热×VPD 同现
- 写代码之前，先交一份简短的方法与实现规格审阅。规格要写清：
  - 用哪个 gridMET 变量、单位，是直接取用还是自行推算
  - 时间和空间上怎么聚合
  - 覆盖率的分母
  - 缺数据时怎么处理
  - 阈值和它的证据依据
  - 数据来源记录、证据等级
  - 允许和禁止的解读
- 规格必须和 4B-0 以及证据登记表保持一致。**不凭空设定 VPD 伤害阈值。**
- 输出先保持简单，只有三种：同时出现、未同时出现、未知。热和 VPD 仍是两个独立的证据层，
  同时出现只说明天气条件同时存在，不证明作物受损。
- **需要用户决定的一点**：判断"同时出现"，必须先定义什么算"高 VPD"。站得住脚的做法有两种，规格里会对比利弊：
  - 相对于气候的百分位。这需要 2.3 的气候缓存，所以两者的基础设施可能要一起建。
  - 明确标注为 C 级、由项目自定的阈值。

### 4B-2.3 降水距平
- 气候基准默认用 **1991–2020**，除非有很强的方法学理由改用别的时期。
- 30 年气候值做成**有版本号的静态缓存**，绝不在每天的流程里重新计算。
  每天的计算方式是：当前的玉米面积天气 × 审定过的气候缓存 → 按面积加权的降水距平证据。
- 要保留这些信息：空间覆盖率、缺失面积的分母、数据来源、基准版本、天气数据版本。
- 降水偏少不叫作物受损。

### 4B-2.4 湿涝，以及播种和发育进度（在 2.5 之前完成）
- 两类证据分开展示：
  - 空间上的湿涝或天气证据
  - USDA 官方的播种和发育背景信息
- 全州进度无法推出局地生育期面积。不得用"天气重叠面积 × 全州生育期百分比"去推算受影响面积。
- 证据不足以支持结论时，保留"未知"。

### 4B-2.5 页面展示
- 等主要证据模块都稳定后再做。页面要把证据链讲清楚，顺序是：
  作物地理 → 天气暴露 → 各项独立的危害证据 → 发育背景。
- 必须出现的两句话："筛查触发不等于作物受损"，"未触发不保证作物安全"。
- 要展示的信息：数据新旧程度、空间覆盖率、证据状态、数据来源、方法版本。
- 非生长季要显示"不在生长季"，不能显示"无风险"。
- 不展示没有依据的综合风险分数。

### 4B-2.6 方法冻结，以及事先写好 4C 验证方案
- 冻结以下内容：
  - 方法版本、证据定义、阈值、基准期
  - 空间方法、覆盖率规则、缺数据的处理
  - 证据术语、页面上的解读文字
- 冻结之后，任何修改都要发布新的方法版本。
- **在看到 2027 年结果之前**，先写好 4C 的验证方案，内容包括：
  - 评估用什么结果、在什么时间窗口
  - 留出数据的规则
  - 成功和失败的标准
  - 缺数据怎么处理
  - 拿什么做对比基准
- 2012–2019 年的数据只用于开发。不根据 2027 年观察到的结果去调整已冻结的方法。

### 2027 生长季
- 用冻结的方法做前瞻性运行，只观察。即使结果和筛查信号对不上，也不在季内调整参数。
- 每次运行都要记录：证据、数据源版本、发布标识、数据修订、缺失情况、覆盖率。

### 4C
- 按事先写好的方案做验证。只有验证之后，才决定某项 Level C 证据是否适合用于告警、
  分级升级规则或通知。不预设一定会接入告警。

## 5. 工作方式

- 每个子阶段单独提 PR 合并进 main。所有新增内容都是附加的，并且有版本隔离。
- 合并前，在分支上手动触发工作流，勾选 `validation_only: true`，用真实数据跑一遍，不部署也不发邮件。
- 合并本身就是用户的批准记录。
